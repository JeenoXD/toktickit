# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a working Requester-facing ticketing experience: a Requester (selected via a temporary
Development Requester selector) can create an IT support ticket with attachments, view their own
tickets in a searchable/filterable/sortable/paginated list, and inspect a read-only ticket detail
screen where they can add or soft-remove attachments. All work is scoped to the Requester role only;
no authentication, IT Staff workflow, or post-creation ticket lifecycle is included.

## 2. Stakeholder Request Interpretation

The IT department wants Requesters to be able to submit real support tickets through a professional,
responsive UI, then track and manage those tickets themselves. Since real login isn't ready until Lab 3,
we simulate "who is using the app" with a Development Requester selector — the student picks one of
several seeded Requesters, and that identity is used for all ticket ownership during the session. The
system must strictly prevent one Requester's tickets from being visible to another.

## 3. Scope

### Included
- Development Requester Selection screen (testing-only identity switch)
- Create Ticket (form, validation, attachment upload, Ticket Number generation)
- My Tickets (list, search, filter, sort, pagination, ownership-scoped)
- Requester Ticket Detail (read-only ticket info, attachment list, add/soft-remove attachment)
- Attachment lifecycle: upload, download (active only), soft removal
- Zen Green theme and reusable UI components (forms, badges, states)

### Excluded
- Authentication: login, logout, passwords, sessions, tokens, real authorization
- IT Staff workflow: dashboards, claiming, IT Priority, ownership transfer
- Ticket collaboration: Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle beyond initial `New` status (resolve, close, reopen, cancel)
- Administration: user/reference-data management

## 4. Functional Requirements

- FR-01: The system shall allow a Requester to select a Development Requester identity before accessing any ticket screen.
- FR-02: The system shall allow the Requester to change the active Development Requester at any time via a "Change Requester" action.
- FR-03: The system shall allow a Requester to submit a new ticket with Category, Related System, Summary, Description, Requested Priority, and optional attachments.
- FR-04: The system shall generate a unique, backend-issued Ticket Number upon successful ticket creation.
- FR-05: The system shall allow a Requester to view a paginated list of only their own tickets.
- FR-06: The system shall allow the Requester to search their tickets by Ticket Number or Summary.
- FR-07: The system shall allow the Requester to filter their tickets by Category, Requested Priority, IT Priority, and Current Status.
- FR-08: The system shall allow the Requester to sort their ticket list by Created Date and Last Updated (ascending/descending).
- FR-09: The system shall allow the Requester to open a read-only Ticket Detail screen for any ticket they own.
- FR-10: The system shall reject any attempt to view or modify a ticket the active Requester does not own.
- FR-11: The system shall allow the Requester to add a permitted attachment to an existing owned ticket.
- FR-12: The system shall allow the Requester to soft-remove one of their own attachments, with the metadata retained but the file no longer downloadable.
- FR-13: The system shall reject files exceeding the type or size limits, or exceeding the maximum active-attachment count.

## 5. Business Rules

- BR-01: The official Ticket Number is generated by the backend and must be unique (format: `TKT-YYYY-NNNNNN`, zero-padded sequence).
- BR-02: A new Ticket begins with Current Status `New`.
- BR-03: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- BR-04: Ticket Date is system-generated at creation time and is read-only thereafter.
- BR-05: A Requester may only be selected in the Development Requester Selection screen if they are marked active; inactive Requesters never appear in the dropdown.
- BR-06: Changing the Development Requester immediately clears and reloads all Requester-scoped data (My Tickets, Ticket Detail access).
- BR-07: A Ticket's `requesterId` is fixed at creation and is never editable afterward.
- BR-08: Ticket Summary is required, trimmed of leading/trailing whitespace, and must be between 5 and 150 characters.
- BR-09: Ticket Description is required, trimmed, and must be between 10 and 2000 characters.
- BR-10: Category and Related System must reference an existing, active record; submission fails if either is missing or invalid.
- BR-11: Requested Priority must be one of `LOW`, `MEDIUM`, `HIGH`.
- BR-12: The system must prevent duplicate double-submission of the same ticket (e.g. disable Submit while the request is in flight).
- BR-13: If ticket creation fails after validation passes (e.g. server/database error), the form retains all entered values so the Requester does not need to retype anything.
- BR-14: If a Ticket is created successfully but an attached file fails to upload, the Ticket is still saved; the failed attachment is reported separately and can be retried from Ticket Detail.
- BR-15: Attachment allowed types are JPG/JPEG, PNG, WEBP, and PDF only; max size 5 MB per file; max 5 active attachments per ticket.
- BR-16: Attachment removal is soft-delete only — the record and its metadata remain, but `removedAt`/`removedReason` are set and the file becomes non-downloadable and non-previewable.
- BR-17: Only the owning Requester may add or remove attachments on their own ticket.
- BR-18: My Tickets pagination defaults to a fixed page size (e.g. 10) and rejects invalid page/pageSize query values by falling back to defaults rather than erroring.
- BR-19: An empty ticket list (Requester has zero tickets) and a no-results state (search/filter matched nothing) must be visually distinguished.
- BR-20: Ticket Detail access for a ticket not owned by the active Requester returns a not-found/forbidden response, not the ticket's data.
- BR-21: In Lab 3, the Development Requester selector will be replaced by real authentication; the `requesterId` association model is designed so this swap doesn't require a schema change.

## 6. UI Specification Summary

See `docs/lab-02/ui-spec.md` for full detail. Summary:
- **App shell:** TokTickIT header (Zen Green `#006B3C`), My Tickets / Create Ticket nav, current Requester name + Change Requester action, responsive mobile nav.
- **Development Requester Selection:** dropdown of active Requesters, loading/empty/error states, Continue button, explanatory "testing only" text.
- **Create Ticket:** system-generated fields visually distinct (read-only styling), classification fields grouped, Summary/Description given full width, attachments below main fields, busy-state Submit button, field-level validation messages.
- **My Tickets:** search bar, filter dropdowns (Category/Requested Priority/IT Priority/Status), sortable columns, pagination controls, Create Ticket action, loading/empty/no-results/failure states, badges for priority/status.
- **Ticket Detail:** read-only header fields, separate Attachments section with add/download/remove actions, distinct visual separation between ticket info and attachment actions.
- **Responsive breakpoints:** Desktop ≥992px, Tablet 768–991px, Mobile <768px, per Section 8.7 of the labsheet.

## 7. Data Changes

New Prisma models (see `server/prisma/schema.prisma` for authoritative definitions):

- **RequesterUser**: `id`, `name`, `email` (unique), `isActive`, `createdAt`
- **Ticket**: `id`, `ticketNumber` (unique), `requesterId` (FK → RequesterUser), `categoryId` (FK → Category), `relatedSystemId` (FK → RelatedSystem), `summary`, `description`, `requestedPriority` (enum), `itPriority` (nullable enum), `currentStatus` (enum, default `NEW`), `createdAt`, `updatedAt`
- **RelatedSystem**: `id`, `name` (unique), `isActive`, `createdAt`
- **Attachment**: `id`, `ticketId` (FK → Ticket), `filename`, `storedPath`, `mimeType`, `sizeBytes`, `uploadedAt`, `removedAt` (nullable), `removedReason` (nullable)
- **Category**: extended from Lab 1 with `isActive` if not already present

Indexes: `Ticket.requesterId`, `Ticket.ticketNumber` (unique), `Ticket.currentStatus`, `Attachment.ticketId`, `RequesterUser.email` (unique). Soft removal represented via nullable `removedAt` timestamp on `Attachment`, never a hard delete.

## 8. API Contract

See `docs/lab-02/api-spec.md` for full detail. Endpoints:

- `GET /api/categories` — active categories
- `GET /api/related-systems` — active related systems
- `GET /api/requesters` — active Development Requesters
- `POST /api/tickets` — create a ticket for the selected Requester
- `GET /api/tickets?requesterId=&search=&category=&requestedPriority=&itPriority=&status=&sortBy=&sortDir=&page=&pageSize=` — paginated, filtered, owned ticket list
- `GET /api/tickets/:id?requesterId=` — one owned ticket
- `POST /api/tickets/:id/attachments` — upload attachment
- `GET /api/tickets/:id/attachments` — attachment metadata
- `GET /api/attachments/:id/download` — download active attachment
- `DELETE /api/attachments/:id` — soft-remove (body includes reason + requesterId for ownership check)

## 9. Acceptance Criteria

- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned.
- AC-04: Given the Summary field is empty, when the Requester submits the form, then a field-level validation message is shown and no API call is made.
- AC-05: Given a Ticket is submitted with one valid and one oversized attachment, when the Requester submits, then the ticket is created and the oversized attachment is rejected with a clear message.
- AC-06: Given the backend is unreachable, when the Requester submits a valid form, then a safe error state is shown and all entered field values are preserved.
- AC-07: Given a Requester has more than one page of tickets, when they navigate to page 2, then a different set of tickets is shown and the URL/query state reflects page 2.
- AC-08: Given a Requester searches for a term matching no tickets, when the search runs, then a distinct "no results" state is shown (not the same as the empty-list state).
- AC-09: Given a Requester removes an attachment with a reason, when the removal completes, then the attachment metadata remains visible but the download action is disabled.
- AC-10: Given a removed attachment, when a direct download is attempted, then the backend rejects the request regardless of frontend state.
- AC-11: Given an inactive Development Requester, when the Requester Selection screen loads, then that Requester does not appear in the dropdown.
- AC-12: Given the Requester changes their Development Requester selection, when the change completes, then My Tickets reloads and shows only the new Requester's tickets.

## 10. Definition of Done

- All FRs and BRs above are implemented and traceable to at least one test in `tests.md`.
- All Acceptance Criteria pass with automated test evidence (unit, API, UI, and at least one E2E).
- No test is skipped, disabled, or commented out in the final `main` branch.
- UI matches `ui-spec.md` and the Zen Green theme at desktop, tablet, and mobile viewports.
- All API responses match `api-spec.md`, including error/status codes.
- README setup and test-run instructions are current.
- All four Issues are peer-reviewed, approved, and merged via `lab2-staging` → one release PR → `main`.
- `docs/lab-02/reviewer.md` and `docs/lab-02/ai-use.md` are complete.

## 11. Assumptions and Decisions

- Ticket Number format chosen as `TKT-YYYY-NNNNNN` for readability and sortability; sequence resets are not required for Lab 2 scale.
- Pagination default page size set to 10, max allowed 50, to keep UI usable without over-engineering.
- IT Priority is nullable and unset at creation (it's an IT Staff concern introduced in a later lab), but the field exists in the schema now to avoid a future migration.
- Attachment storage uses local disk under a server-side uploads folder for Lab 2; no cloud storage is required at this stage.
- Ticket Number generation (`prisma.ticket.count()` + offset) retries on a unique-constraint collision (up to 5 attempts) rather than relying on a database sequence, since concurrent creation under Lab 2's test load occasionally produced duplicate candidate numbers.
- Playwright E2E/responsive tests run with a single worker (`workers: 1`) rather than in parallel, since parallel workers creating tickets simultaneously caused the same kind of collision against the shared test database.
